### A1 — All ids are UUID (v7); only `users.telegram_id` stays BIGINT/Long — **DONE**

Every one of the 20 entities carries `@UuidGenerator(style = UuidGenerator.Style.VERSION_7)`
on a `private UUID id` (checked mechanically: no entity file in `entity/` lacks
`VERSION_7`). Every changeset declares `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`

### C6 — Slot price order: owner's slot price → promotion → pricing rule → base — **PARTIAL**

2. The requirement reads as a precedence list (promotion *instead of* the rule);

### C8 — Opening hours that close after midnight (`close_time <= open_time`) — **how the code handles them now** (not a status; not decided)

Three different layers, consistent with each other:

1. **The stadium can be saved that way.** Neither `CreateStadiumRequest` nor
   `UpdateStadiumRequest` has a cross-field check (both declare `openTime` and
   `closeTime` as plain `LocalTime`), `StadiumService.create`/`update` do not
   compare them, and `003-create-stadiums.sql` has no CHECK constraint. So an
   owner can create a stadium with `open_time = 22:00, close_time = 02:00` and
   get a 200 back.
2. **Availability then returns zero slots, silently.**
   `service/AvailabilityService.java:90` is `while (slotStart.isBefore(stadium.getCloseTime()))`,
   which is false on the first iteration when `close <= open`. The response is a
   well-formed `AvailabilityResponse` with an empty `slots` list — no error, no
   explanation.
3. **Booking is refused with an explicit message.**
   `service/BookingWindowValidator.java:45-49`:
   `if (!open.isBefore(close)) throw new BadRequestException("Stadium has no bookable hours")`.
   Separately, every booking must end on the same calendar day and at or before
   `close_time` (`:53-57`), so no booking can ever cross midnight even for a
   normal window. `BookingSeriesService.createSeries` (`:80-89`) applies the
   same rule with the message *"Requested time is outside the stadium's operating
   hours"*.

Net effect today: such a stadium is **fully unbookable but still publicly
listed**, and the only hint is an empty availability response. The class's own
Javadoc documents this as deliberate alignment with availability.

## D. Ordinary bookings

### D1 — Any number of consecutive whole hours (min 1), on the hour, inside opening hours, no closure overlap — **DONE**

`service/BookingWindowValidator.java` is the single gate for app, manual,
recurring and game bookings:

- `duration < 1` → 400 (`:35-37`)

The upper bound was removed in `018-booking-duration-unbounded.sql`
(`CHECK (duration_hours >= 1)`). Max 4 weeks ahead at
`service/BookingService.java:83-88`.

### D2 — EXCLUDE constraint + `saveAndFlush` → 409, with the multi-hour message — **DONE**

- Constraint: `008-create-bookings.sql` —
  `EXCLUDE USING gist (stadium_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (status IN ('pending','confirmed'))`.
- `saveAndFlush` so the violation surfaces inside the `try`:
  `service/BookingService.java:110` (app), `:158` (manual),
  `service/GameService.java:302` (game auto-booking).
- `SlotAlreadyBookedException` → **409** at
  `exception/GlobalExceptionHandler.java:44-48`.
- Message: `BookingService.overlapMessage` (`:308-312`) returns
  *"One or more of the selected hours is already booked"* for `duration > 1`,
  *"Slot is already booked"* for 1 hour. The fallback handler
  (`GlobalExceptionHandler.java:87-92`) also recognises `bookings_no_overlap` by
  name and answers 409.

### D3 — 10-minute hold + expiry job; a payment after expiry confirms if the slot is free, otherwise refunds — **PARTIAL**

The hold and the job are right:
- `expires_at = now + app.booking.hold-expiry-minutes` (default 10) at
  `service/BookingService.java:104`; `config/AppProperties.java` `holdExpiryMinutes = 10`.
- `scheduler/BookingExpiryJob.java:30-47` runs every 60 s, flips
  `pending` + `expires_at < now` to `expired`, and is idempotent (expired rows
  stop matching). 2 passing tests.

**The late-payment rule is not implemented.** The webhook path does not go
through `BookingService.confirmBooking` (which *does* guard expiry at
`service/BookingService.java:185-187`). It calls
`PaymentService.confirmPaidBooking` (`service/PaymentService.java:271-274`):

```java
booking.setStatus("confirmed");
booking.setExpiresAt(null);
bookingRepository.save(booking);
```

No status check, no expiry check, no slot-free check, no refund. Consequences:

- A webhook arriving after expiry silently resurrects an `expired` booking.
- If the freed slot has since been taken, that UPDATE trips
  `bookings_no_overlap`, so the webhook fails with a `DataIntegrityViolationException`
  → 409 "Data conflict" to the payment provider, and the player's money is
  neither applied nor refunded.

## F. Team vs team games

### F1 — Join requires `teamId`; caller must lead it; it can't be the waiting team; team B saved on the game — **DONE**

`GameService.acceptAsTeamB` (`service/GameService.java:384-402`), reached by
joining with `side = "b"` (`:153-155`):

- `teamId == null` → `BadRequestException("teamId is required to join as team B")` (`:385-387`)
- caller must be that team's leader → `ForbiddenException("Only the team leader can accept")` (`:390-392`)
- `teamId == game.teamA` → `BadRequestException("A team cannot play against itself")` (`:393-395`)
- already has a different team B → rejected (`:396-398`)
- `game.setTeamB(teamB); gameRepository.save(game)` (`:399-400`)

Fixed in `642e295`; covered by `GameServiceTest` (25 tests).

### F2 — Per team: platform fee + owner advance (min/2 or price/2) in app; remainder (price − min)/2 later, in app or cash — **MISSING**

What exists instead (`PaymentService.gameShareAmount`, `:299-310`):

```java
if ("team_vs_team".equals(game.getType())) {
    int pct = participant.getSide() == Side.B ? 100 - game.getCreatorSharePct() : game.getCreatorSharePct();
    return (int) ((long) total * pct / 100) + fee;   // fee = game.serviceFeePerPerson
}
```

i.e. each leader pays a `creator_share_pct` slice of the **full** pitch price plus
a flat per-leader service fee — a single up-front charge. There is no platform fee
from settings, no owner advance derived from `min_booking_amount` (which doesn't
exist), no remainder, and no cash marking.

### F3 — States WAITING (slot free) / CONFIRMED (booking exists) / CANCELLED; confirmed can return to WAITING; payments tracked per game *and team* — **PARTIAL**

Working:
- WAITING ≡ `status = 'open'` and the slot is genuinely free: `createGame` only
  checks for an overlap (`service/GameService.java:94-96`) and never writes a
  booking.
- CONFIRMED creates the booking: `confirmGame` (`:289-317`) inserts a
  `source = 'game'`, `status = 'confirmed'` booking and sets `game.bookingId`.
- CANCELLED via `cancelled_slot_taken` / `cancelled_by_creator` / `cancelled_not_filled`.

Missing:
- **No path from CONFIRMED back to WAITING.** `cancelGame` (`:226-228`) requires
  `status = 'open'`; nothing anywhere sets a game back to `open`.
- **Payments are tracked per participant (user), not per (game, team).**
  `game_participants.payment_id` (`010-create-game-participants.sql`) is one
  payment per user row; `isFullyFunded` infers team payment by asking whether
  *any* participant on side A and side B is `PAID`
  (`service/GameService.java:319-331`). There is no per-team payment record, so
  "team B has paid its advance but not its remainder" is not representable.

### F4 — Creating HOLDS the creator's payment; joining books the slot, then charges the joiner, then captures the hold; a taken slot charges nobody new — **CONFLICT**

The order is essentially reversed, and no hold exists:

1. `createGame` takes **no payment at all** — it inserts the game plus a
   `JOINED` participant (`service/GameService.java:129-131`). The creator pays
   later via `POST /api/games/{id}/pay`.
2. There is no hold/capture/release anywhere (see E1).
3. Both teams pay **first**; only when `isFullyFunded(game)` is true does
   `handleGamePaymentConfirmed` call `confirmGame`
   (`:247-249`), which *then* attempts the booking (`:302`).
4. If the slot was taken meanwhile, the `DataIntegrityViolationException` handler
   (`:311-316`) cancels the game and refunds **both** teams — which already paid.
   So the failure mode the requirement is designed to prevent (charging people for
   a slot you can't get) is exactly what happens today.

### F5 — WAITING ends: slot booked → cancel + full refund; no opponent 3 h before start → auto-cancel + refund; waiting team cancels → full before the deadline, nothing after — **PARTIAL**

| Sub-rule | Status |
|---|---|
| Slot booked directly → game cancelled, everything back | **Done** — `GameService.cancelGamesOnSlot` (`:253-266`) sets `cancelled_slot_taken` and calls `refundPaidParticipants`; invoked from `BookingService.createBooking:117` and `createManualBooking:165` |
| No opponent **3 hours before** the start | **Conflict** — the timeout fires *at* the start time: `cancelUnfilledGames` (`:270-285`) queries `findByStatusAndStartsAtBefore("open", now)`, run every 60 s by `scheduler/GameTimeoutJob.java:22-23`. Nothing uses a 3-hour offset. |
| Waiting team cancels: full refund before the deadline, nothing after | **Conflict** — `cancelGame` (`:221-236`) always calls `refundPaidParticipants` with no deadline check, and only the *creator* may call it (`:223-225`), so the joining team cannot cancel at all |

### F6 — A team cancels a CONFIRMED game (three deadline bands); owner cancelling refunds both teams — **MISSING**

A confirmed game cannot be cancelled by a team at all: `cancelGame`
(`service/GameService.java:226-228`) throws
`BadRequestException("Only an open game can be cancelled")`. There is no
back-to-WAITING transition (F3) and no 3-hour band logic.

The owner path is also incomplete: `BookingService.cancelByOwner` (`:227-250`)
refunds the **booking** payment (of which there is none for a game — the money is
in `game_share` payments), leaves the `games` row `confirmed`, and never touches
`game_participants`.

### F7 — Joining closes 3 hours before the start; games starting within 3 hours aren't listed; the rule is team-vs-team only — **MISSING**

No 3-hour rule exists anywhere. `joinGame` (`service/GameService.java:140-147`)
checks only `status == 'open'` and "already joined".

Separately, **team-vs-team games are not listed for opponents at all**:
`createGame` sets `isPublic = TYPE_OPEN.equals(type)` (`:112`), so a

### F8 — Chat opens when the game is confirmed and closes after the game — **PARTIAL**

`GameMessageService` restricts chat to `team_vs_team` (`:44-46`) and to
participants (`requireParticipant`), and closes it once the status is neither

But it **opens too early**: `service/GameMessageService.java:47` is

```java
if (!"open".equals(game.getStatus()) && !"confirmed".equals(game.getStatus())) {
```

so the two teams can chat while the game is still WAITING, before confirmation.
5 passing tests, which encode the current (open-or-confirmed) behaviour.

### F9 — The "open" game type is not exposed in any player endpoint — **CONFLICT**

It is fully exposed:

  `@Pattern(regexp = "casual|open|team_vs_team")`, so `POST /api/games` accepts it.
